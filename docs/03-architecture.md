# Архитектура и стек

## Решение: модульный монолит

**Один FastAPI-бэкенд + одна база Postgres + один React-фронтенд. Никаких микросервисов.**

### Почему микросервисы сейчас — ошибка

| Фактор | Микросервисная реальность | Наша реальность |
|---|---|---|
| Команда | решают проблему N команд, мешающих друг другу | 1 человек — декаплить нечего, координация бесплатна |
| Ops | service discovery, распределённая трассировка, CI на сервис | 80% времени уйдёт на инфраструктуру вместо продукта |
| Деньги | каждый сервис = отдельный деплой = отдельный инстанс | free tier даёт ОДИН веб-процесс; «сплит» = два холодно стартующих бесплатных дино, говорящих по HTTP без причины |
| Отказы | сетевые партиции, частичные отказы, eventual consistency | вызов функции на localhost не может затаймаутить |
| Данные | БД на сервис, саги для транзакций | вся БД < 50 МБ |
| Обучение | дебаг распределённых систем — сложнейший навык бэкенда | первокурснику нужно учить SQL, HTTP и моделирование данных — всё это учится в монолите |

### Что значит «модульный» на практике

Границы — папками, не сетью:

```
backend/
  app/
    main.py               # app factory, подключение роутеров
    core/                 # config, db session, security (JWT)
    modules/
      catalog/            # вузы, требования, стоимость, дедлайны
        router.py         #   HTTP-слой
        service.py        #   бизнес-логика (поиск, eligibility)
        models.py         #   SQLAlchemy-модели
        schemas.py        #   Pydantic-схемы
      users/              # профиль (баллы, бюджет)
      favorites/          # избранное
      admin/              # импорт курации
    ingest/               # пайплайн данных — скрипты, НЕ часть веб-приложения
```

**Правило модульности:** модуль не импортирует чужие `models.py` напрямую — только функции чужого `service.py`. Эта дисциплина превращает будущий вынос модуля (если понадобится) в copy-paste, а не переписывание.

### Путь миграции при росте

1. Первый кандидат на вынос — не «сервис», а **пайплайн данных** → отдельный cron-воркер (он уже изолирован в `ingest/`).
2. Затем кэш/реплика на чтение, если упрёмся в чтения.
3. Только при реальном масштабе команды — вынос самого «горячего» модуля за тот же REST-контракт.

До ~100k MAU ничего из этого не понадобится.

## Стек (финальный выбор)

Исходные предпочтения: Python, TypeScript, React, Vite, PostgreSQL, Redis, MongoDB. Взято подмножество:

| Слой | Выбор | Обоснование |
|---|---|---|
| Backend | **FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic v2** | Авто-документация OpenAPI на `/docs` — бесплатная песочница API, огромный плюс для обучения. Лучшая документация в современном Python. Django-админку заменяет table editor Supabase — меньше фреймворковой магии |
| БД | **PostgreSQL** (Supabase в проде, SQLite локально) | Данные насквозь реляционные (вуз → требования → стоимость → дедлайны), ядро продукта — мульти-полевая фильтрация = родная территория SQL. JSONB закрывает «гибкие» поля |
| **MongoDB** | ❌ **отброшен** | Нет документо-образных данных; вторая БД удваивает ops и моделирование ради нуля пользы |
| **Redis** | ⏸ **отложен (вероятно навсегда)** | Кэшировать 300 строк, меняющихся раз в неделю — не проблема. Если понадобится — сначала HTTP Cache-Control и in-process кэш. Очереди фазы 2 закрываются Postgres или cron-скриптом |
| Frontend | **React 18 + TypeScript + Vite + Tailwind CSS 4 + TanStack Query** | Самая документированная связка для новичка; TanStack Query убирает 80% ручного fetch/loading/error-кода |
| SSR/Next.js | ❌ не сейчас | SPA достаточно для MVP. SEO важно с фазы 3 — тогда пререндер ~300 страниц на билде или миграция |
| Поиск | **Postgres FTS + pg_trgm** | см. ниже |
| Auth | **Supabase Auth** | см. [06-api.md](06-api.md) |
| Аналитика | PostHog Cloud free / Umami + своя таблица `outbound_clicks` | критичные для монетизации данные храним у себя |

## Поиск: Postgres, не Elasticsearch

- Корпус: ≤300 строк в v1, ≤5 000 в обозримом будущем. Elasticsearch создан для миллионов документов; здесь он добавил бы JVM-сервис **без бесплатного тарифа**, код синхронизации индекса и второй язык запросов — чистые издержки.
- Реальная сложность поиска — опечатки и кириллица: «Масачусетс», «Стэнфорд», «каист». Это решает **pg_trgm** (trigram similarity) + курируемая колонка **`aliases`** с русскими написаниями — для 300 вузов рукописные алиасы бьют любой поисковый движок.
- Все структурные фильтры (страна, SAT ≤ X, бюджет ≤ Y) — обычные WHERE по индексам, поисковый движок там ничего не добавляет.
- Если когда-нибудь понадобится движок — следующий шаг Meilisearch/Typesense, не Elasticsearch.

Реализация сейчас (см. `catalog/service.py`): ILIKE по `name_en`/`name_ru`/`city`/`aliases`; при переходе на Postgres добавить GIN trigram-индекс и `similarity() > 0.3`.

## Локальная разработка без боли

- Локально БД = **SQLite** (файл `dev.db`, создаётся сам) — брату не нужно ставить Postgres/Docker, порог входа нулевой.
- Один флаг `DATABASE_URL` переключает на Supabase Postgres.
- В dev таблицы создаются `create_all` на старте; в проде — `alembic upgrade head`.
- Vite-proxy `/api` → `localhost:8000` — без CORS-возни локально.

## Что учить первокурснику (по неделям)

1. **Неделя 1:** туториал FastAPI (официальный), Pydantic-схемы, Alembic-миграции.
2. **Недели 2–3:** SQLAlchemy 2.0 (unified tutorial), react.dev + fullstackopen.com.
3. **Постоянно:** читать свой `/docs` (OpenAPI) — видно, как API выглядит снаружи.

Весь стек — «boring technology» с изобилием туториалов. Это осознанный выбор.
